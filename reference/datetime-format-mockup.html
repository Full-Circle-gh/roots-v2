What the measurement actually says

  • The Placed column gets narrower, not wider. B measures 108px against today’s 116px — 8px saved. Dropping the redundant “2026-” from every row more than pays for “PM”. The density worry was wrong here.
  • The cost is real, but it is only the standalone clocks. A rider time goes from 35px (14:26) to 56px (3:40 PM) — +60% on that one element. That is the entire trade, and it lives in the Delivery column, not in Placed.
  • So the question narrows. It is not “is US format too wide for Orders” — it is “is a 21px wider rider clock worth never having to write down an exception”.

Year rule: the year is shown only when the date is not in the current year. Without it, every ops table grows a redundant “, 2026” on every row.

What never changes

  • machine stays ISO forever. Date inputs, CSV and XLSX exports, filenames, and every payload going to Meituan, Guanyi, JD or the API. Localising these breaks integrations silently.
  • Always the store’s wall clock. Timestamps are stored UTC and rendered in the store’s own timezone — never the operator’s browser. This is the one thing the current code already gets right.
  • Never a locale-less call. There are 71 toLocaleString() calls today with no locale argument. Those render in the operator’s OS language, so the same screen looks different on two laptops in the same office. This becomes a grep in the audit.
  • Never a hard-coded locale string. Four en-GB calls ship on the Dashboard today. Nobody chose British — it was typed once and copied.
