# Product data pull — where every field came from

Generated by `build_pull.py`. Re-run with `python3 docs/product-data-pull/build_pull.py`.

## What is NOT on this machine

- **No live database.** `database.js:7` opens `data/roots.db` (SQLite, created at boot).
  That directory does not exist in this checkout.
- **No `.env` and no API credentials.** The code reads `TACET_PG_HOST` / `TACET_PG_USER` /
  `TACET_PG_PASSWORD` / `TACET_PG_DATABASE` / `TACET_PG_PORT` and `ROOTS_DB`; none are set.
  `psql` and `pg_dump` are installed but there is nothing to point them at.
- Consequence: this pull is assembled **entirely from flat files committed to the repo**, not
  from the live rootskitchenchina.com system. Every value is copied verbatim; nothing is
  inferred, derived, or filled in.

### Deliberately not used as a sales source

`scripts/meituan_tianhe_*.json` and `scripts/meituan_yuexiu_*.json` carry order-level records
only — `item_count`, `gross_amount`, `product_total` and settlement rows, with **no per-line SKU
breakdown**. They cannot produce sales volume per SKU, so no Meituan volume is reported.

## Sales window

Requested: the 6 months ending 2026-08-13, i.e. **2026-02-13 → 2026-08-13**.

The window is applied as asked, but the underlying data stops earlier — the latest sales record
anywhere on this machine is 2026-05-30 (gzgrocery) and 2026-04-29 (miniapp). **June, July and
August 2026 have no data here at all**, so the reported figures cover roughly the first half of
the requested window. They are not a full 6 months and should not be read as one.

Columns are kept separate per channel (`sales_units_gzgrocery`, `sales_units_miniapp`) rather
than summed, because the two channels are counted from different record types.

## Products the catalogue file omits

`products_import.json` holds 259 rows, but it is not the full catalogue. **43 further SKUs are
real products that appear only in the sales or variant data**, giving **302 distinct products**.
They are included in the pull and marked in the `source` column; `gaps` flags them
`ABSENT FROM CATALOGUE FILE`. 26 of the 43 recorded sales inside the reporting window — those
units were being dropped entirely before these rows were added.

Most are **size variants** of a catalogue parent sold under their own SKU (small / medium / big
coconut yogurt, kombucha 300ml vs 1000ml, nut and nut-butter jar sizes); `parent_sku` and
`variant_label` carry the link where `gzgrocery_import.json` records it. A handful are
standalone products with no catalogue row at all — `4-340` Himalaya Pink Salt, `4-520` Activated
Charcoal, `7-600` LUÜNA Organic Cotton Day Pads, `2-9` Frozen Cheese Cake, `4-33` Chunky Granola.
`4-680` / `4-690` are notable: the catalogue file contains the **bundle** `（4-680）+（4-690）`
but neither of the two peanut butters it is built from.

Two identity rules keep the count honest rather than inflated:

- **`sku_aliases` is applied before comparing.** `3-50` looks like a missing product but is an
  alias of `2-2` Quinoa Patties, already in the pull. It is not counted twice.
- **One catalogue row wraps its SKU in fullwidth parentheses** — `（4-530）` — which is the same
  product as `4-530` in the sales data. It is normalised and merged, so Prebiotic Fiber is one
  row, not two. Genuine bundle SKUs (`（5-160）+（5-170）+（5-180）`) are left intact.

## Parsing rules

- `pack_size_net_weight` — the value of a literal `Net weight:` / `Net volume:` / `Net content:`
  line, else the `NET CONTENT & PACKAGING` section body.
- `storage_temp` — the value of a literal `Storage:` line, else the `STORAGE` /
  `STORAGE & SHELF LIFE` section body. Verbatim, including free-text instructions.
- `ingredients` — the `INGREDIENTS` section body, else a literal `Ingredients:` line.
- Unfilled authoring placeholders (`[fill]`, `TBD`, `XXX`) are treated as **missing**, not as
  values, and are recorded in `unfilled_placeholders`.

## Known catalogue caveats

- The admin screenshot shows 249 products / 241 active; the spine file has 259, all with
  `status: Active`, and the reconciled total is 302. All three numbers disagree, so the spine
  file is a different vintage than the live catalogue and none of this replaces a live export.
- 48 rows have no real SKU and fall back to an `EXT-…` external id or a bundle expression.
- Rows sourced outside the spine have no `category`, `barcode`, `stock_qty`, `tags` or
  `free_of` — those fields exist only in `products_import.json`, so they are left empty rather
  than guessed.
